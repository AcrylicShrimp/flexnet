# Tendermint Consensus V2 Safety Contract

## Status

This document is the normative safety contract for
`crates/flexnet-consensus-v2`.

The pinned reference is Algorithm 1 and the safety proof in:

- [The latest gossip on BFT consensus, arXiv:1807.04938v3](../references/tendermint/1807.04938v3-the-latest-gossip-on-bft-consensus.pdf)

The paper is authoritative for safety. Local liveness mechanisms may differ,
but they must reduce their results to the evidence and transitions defined by
this contract.

This document distinguishes three claims:

1. `transition` preserves local Tendermint safety state.
2. External evidence and signing layers satisfy the assumptions required by
   `transition`.
3. The composition satisfies Tendermint Agreement and Validity.

Claim 1 alone is not sufficient to make claim 3.

## Audit Result As Of 2026-08-13

### Local transition safety: PASS under the typed-input contract

The implemented transition rules preserve the local lock, vote, valid-value,
round, and terminal-decision invariants documented below. Directed tests,
replay sequences, and bounded input-sequence exploration cover this claim.

### Full Tendermint safety: NOT YET ESTABLISHED

The full Agreement and Validity claim remains open until all of these obligations
are implemented and tested:

1. The evidence layer authenticates, scopes, deduplicates, and counts voting
   power for every certificate.
2. A durable signer prevents conflicting local votes across restart, rollback,
   and concurrent execution.
3. The initial four-validator composition passes adversarial model tests.
4. No reactor, catch-up, sync, or chain path can bypass typed evidence readiness
   before voting or committing.

This is an explicit completion checklist, not a defect in the separation between
the safety core and its external evidence layers.

## Scope

This contract covers safety for one fixed validator set and one consensus
height. It does not specify:

- timeout durations or timer scheduling
- gossip, retransmission, or peer selection
- round catch-up policy
- height sync or snapshot sync
- proposer scheduling
- validator-set changes
- block construction policy

Those are liveness or integration concerns unless they violate an input
precondition listed here.

## Paper Safety Properties

The implementation must preserve both safety properties stated by the paper:

### Agreement

No two correct validators decide different blocks at the same height.

### Validity

Every block decided by a correct validator satisfies the deterministic chain
validity predicate for that height.

Termination is a liveness property and is intentionally outside this contract.

## Proof Assumptions

The paper's Agreement and Validity proofs apply only while all of these
assumptions hold:

1. The total Byzantine voting power is at most `f`, and total voting power is
   greater than `3f`. The paper presents the `n = 3f + 1` case.
2. Every quorum contains at least `2f + 1` voting power. Therefore any two
   quorums intersect in at least one correct validator.
3. Validator identities and signatures are authenticated.
4. Voting power is counted once per validator in each quorum.
5. A correct validator emits at most one prevote and one precommit for each
   `(height, round)`.
6. The same validator key cannot violate assumption 5 after restart, rollback,
   or concurrent execution. Durable signing state must enforce this.
7. Proposal and vote hashes bind to exactly one block value. Hash collisions
   and ambiguous canonical encodings are outside the fault model.
8. `valid(block)` is deterministic for all correct validators at the same
   height and chain state.
9. Evidence is scoped to one exact height, round, vote type, and target.
10. The reactor emits a typed core input only after every precondition assigned
    to that input has been verified.

If any assumption is absent from code or tests, the full Tendermint safety claim
remains open even when all `transition` tests pass.

## Normative Local Invariants

The following invariants are the stable contract that implementation and tests
must preserve.

### S1: Height isolation

A core instance handles exactly one height. Evidence from another height cannot
change its state or produce a vote or commit effect. A new height starts with no
lock and no valid proposal.

### S2: Single vote per round and type

A correct validator emits at most one prevote and at most one precommit for a
given `(height, round)`. Replayed, reordered, or duplicated inputs cannot cause
a second vote effect for that vote type and round.

This invariant must also survive process restart through the signing layer.

### S3: Proposal validity before non-nil prevote

A non-nil prevote is emitted only for a proposal whose proposer, signature,
height, round, justification, block hash, and chain validity have already been
verified.

### S4: Lock-restricted proposal acceptance

For a fresh proposal `(block, round)`:

- an unlocked validator may prevote `block`
- a validator locked on `block` may prevote `block`
- a validator locked on another block must prevote nil

For a proposal justified by a prevote quorum at `valid_round`:

- an unlocked validator may prevote `block`
- a validator locked on `block` may prevote `block`
- a validator locked on another block may prevote `block` only when
  `valid_round > locked_round`
- otherwise it must prevote nil

Algorithm 1 line 29 prints `lockedRound <= validRound`, while the explanatory
text and safety argument describe a "more recent" possible decision value with
`validRound > lockedRound`. For a valid protocol history, a conflicting quorum
at the exact locked round is impossible by quorum intersection and single-vote
rules. Flexnet uses the strict `>` form. It is safety-equivalent on reachable
valid histories and rejects the impossible equality case conservatively.

### S5: Precommit prerequisite

A non-nil precommit for `(round, block)` is emitted only after both are locally
ready:

1. a valid proposal for `block` in `round`
2. a verified quorum of prevotes for `block` in the same `round`

The validator's own earlier prevote target does not have to equal `block`.
Quorum evidence determines the precommit target.

### S6: Atomic lock creation

Immediately before emitting a non-nil precommit for `(round, block)`, the core
sets:

```text
locked_round = round
locked_block = block
```

A proposal, prevote, timeout, nil quorum, or valid-value update cannot create,
clear, or rewrite a lock.

### S7: Lock persistence

A lock survives nil prevotes, nil precommits, timeouts, and round changes within
the same height. It is reset only after deciding the height or abandoning the
height through a separately verified height-sync operation.

"Unlocking" in Tendermint means permission to prevote a different justified
proposal. It does not mutate the stored lock immediately. The lock changes only
when a later non-nil precommit is emitted after a matching proposal and prevote
quorum are ready.

### S8: Valid proposal monotonicity

`valid_proposal` records the highest round in which a valid proposal and its
matching non-nil prevote quorum were locally ready. It changes only to a
strictly higher round and never changes on nil evidence or timeout.

It is a proposer hint for liveness. It is not a lock and cannot itself authorize
a commit.

### S9: Nil isolation

Nil evidence may advance the local voting stage or allow a later round, but it
cannot:

- create or clear a lock
- create or replace a valid proposal
- commit a block

### S10: Decision prerequisite

A block decision for `(height, round, block)` requires both:

1. a locally available and validated proposal/block for that exact value
2. a verified quorum of precommits for the same `(height, round, block)`

A precommit certificate by itself may be retained while the matching block is
fetched, but it must not produce the final commit/application effect until the
block is available and passes `valid(block)`.

### S11: Decision finality within a core instance

After deciding a block, the core is terminal for that height. Later proposals,
quorums, and timeouts cannot emit another vote or a different commit.

### S12: Round and stage binding

Proposal, prevote-quorum, and timeout transitions that emit votes are bound to
the core's current round and expected stage. Stale or future input cannot cause
a vote in the current core. A commit certificate may be recognized from an
earlier round only because a valid decision is terminal for the whole height.

## Typed Input Contract

Raw network messages never enter the safety core. Each input is a claim that
the external validation and evidence layers have already established the facts
below.

### `ProposalReady`

The exact proposal is retained locally and all of these facts are established:

- proposer, signature, height, and round are correct
- block hash matches the retained block
- the retained block satisfies the chain validity predicate
- for a justified proposal, `0 <= valid_round < proposal_round`
- its prevote quorum is valid for the same height, `valid_round`, and block

### `PrevoteQuorumReady(Block)`

The exact proposal and block are retained and validated, and a deduplicated
quorum of authenticated prevotes exists for the same height, round, and block.

This is deliberately stronger than "a quorum hash was observed." It encodes the
complete prerequisite of Algorithm 1 line 36 so the core can safely update
`valid_proposal`, lock, and precommit without owning an evidence store.

### `PrevoteQuorumReady(Nil)`

A deduplicated quorum of authenticated nil prevotes exists for the exact height
and round.

### `PrecommitQuorumReady(Block)`

The exact proposal and block are retained and validated, and a deduplicated
quorum of authenticated precommits exists for the same height, round, and
block.

This is the complete decision prerequisite of Algorithm 1 lines 49-51. If the
certificate arrives before the block, the evidence layer retains it and emits
this input only after the matching valid block is ready.

### `PrecommitQuorumReady(Nil)`

A deduplicated quorum of authenticated nil precommits exists for the exact
height and round. This is round-progress evidence only.

### `TimedOut`

The timeout belongs to the exact core height, round, and stage for which it was
armed. A stale or mismatched timeout has no safety effect.

## Responsibility Map

| Safety obligation | Owning layer | Required verification |
| --- | --- | --- |
| Proposal authentication and proposer selection | Message validation | Signature, validator, height, round, proposer |
| Block validity | Chain validation | Parent, deterministic execution, state root, protocol rules |
| Justified proposal | Evidence validation | Matching prior-round proposal and prevote quorum |
| Prevote quorum | Evidence store | Same height/round/target/type, unique validators, quorum power |
| Precommit quorum | Evidence store | Same height/round/target/type, unique validators, quorum power |
| No local double vote | Durable signer | Persist before signing; reject conflicting vote after restart |
| Lock and valid-value rules | Consensus core | `CoreState` plus typed input contract |
| Final decision | Consensus core and chain | Ready block plus matching precommit quorum |
| Height reset | Runtime/sync | Replace core only after verified commit or verified sync |

weaker evidence.

## Required Test Structure

Safety tests are organized in proof order rather than source-branch order.

### Layer 1: Typed transition rules

Directed tests pin every normative local rule:

- proposal acceptance under each lock and valid-round relation
- one transition from propose to prevote
- non-nil precommit atomically creates the matching lock
- nil paths preserve lock and valid proposal
- valid proposal updates only from a higher ready quorum
- round changes preserve lock and valid proposal
- commit requires block-ready precommit evidence and becomes terminal

### Layer 2: Input-sequence invariants

Bounded exhaustive or property tests apply reordered, duplicated, stale, and
future inputs and assert:

- at most one prevote per round
- at most one precommit per round
- at most one commit per height
- locks change only with a matching non-nil precommit effect
- lock rounds and valid rounds never regress
- nil and timeout inputs never mutate a lock
- no effect is emitted for the wrong current round
- committed state is absorbing

### Layer 3: Certificate and signer invariants

Tests outside `transition` must establish:

- duplicate validator votes do not increase voting power
- mixed height, round, type, or target votes cannot form a certificate
- insufficient voting power cannot form a certificate
- invalid signatures and non-validator signatures are rejected
- two conflicting local votes for one height/round/type cannot be signed,
  including after restart
- a `Ready(Block)` input cannot be produced without the matching validated
  proposal and block

### Layer 4: Four-validator adversarial model

For the initial equal-power network (`n = 4`, `f = 1`), a bounded model test
must generate message reordering, duplication, omission, one Byzantine voter,
and multiple rounds. Across every explored trace it must assert that no two
correct validators commit different blocks at one height.

This is not a mathematical proof for arbitrary executions, but it checks that
the composition matches the paper's proof assumptions in the concrete system.

## Completion Gate

Flexnet may claim that consensus v2 has a safety implementation based on the
pinned Tendermint algorithm only when all of the following are true:

1. Every typed input satisfies the exact contract in this document.
2. All Layer 1 and Layer 2 transition tests pass.
3. Certificate and durable-signer implementations exist and pass Layer 3.
4. The four-validator adversarial model passes Layer 4.
5. The chain validity predicate used before `Ready(Block)` and before block
   application is deterministic and covered by chain tests.
6. A review confirms that no liveness path can bypass typed evidence creation.

Until then, the precise allowed statement is narrower:

```text
The implemented and tested transition rules preserve their documented local
safety invariants under trusted typed-input assumptions.
```
