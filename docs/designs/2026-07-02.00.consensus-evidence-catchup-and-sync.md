# Consensus Evidence, Catch-Up, And Sync

## Design Goal

Define the production-oriented consensus foundation for Flexnet before replacing
or reshaping the current working prototype.

The immediate prototype already has the core Tendermint-style shape:

- proposal
- prevote
- precommit
- lock
- polka-like justification
- quorum-based commit

The problem is not that the happy path is missing. The problem is that the
evidence lifecycle is still implicit and scattered. Delayed, duplicated, or
reordered messages expose unclear ownership boundaries around future evidence,
round catch-up, commit propagation, and height catch-up.

This design fixes the foundation by making all progress evidence-driven.
Future fast paths are allowed, but they must be expressed as additional derived
actions from verified evidence, not as ad hoc branches in the state machine.

## Non-Goals For The Next Slice

- Do not implement open peer discovery.
- Do not implement validator set changes.
- Do not implement snapshot state sync yet.
- Do not optimize bandwidth before the protocol boundaries are correct.
- Do not treat random fast paths as protocol rules.

Validator sets remain fixed and ordered for now. Voting power remains equal.

## Core Principle

All non-local consensus progress must follow this shape:

```text
signed evidence received
-> stateless validation
-> contextual validation
-> store in EvidenceStore
-> derive certificates and safe actions
-> ConsensusCore applies only safety-preserving transitions
```

A fast path is acceptable only if it can be described as:

```text
new evidence enables a new safe DerivedAction
```

Fast paths must not bypass certificate validation, lock rules, or chain
verification.

## Safety And Liveness Boundary

The consensus design must keep safety and liveness separate.

Safety is the contract that a node never commits an invalid or conflicting
block. It is enforced by `ConsensusCore` using only validated evidence,
certificates, and local safety state.

Liveness is the machinery that keeps enough valid evidence flowing into the
system. It is provided by message reception, timeout scheduling, gossip,
round catch-up, commit catch-up, and block sync.

The rule is:

```text
liveness layers may use many paths to obtain evidence
safety core uses one set of rules to validate evidence and transition state
```

Therefore, a new catch-up path must not introduce a separate safety rule. It
must provide evidence that can be verified by the same evidence model and then
reduced to the same small set of derived actions.

The implementation posture is:

```text
safety is copied from a validated consensus algorithm
liveness is engineered around the local system
```

Consensus safety rules are not a place for local creativity. Lock rules,
valid-round rules, quorum rules, proposal justification, and commit rules must
track the selected Tendermint-style algorithm closely enough that the safety
argument remains recognizable.

Liveness machinery may be local and pragmatic. Gossip strategy, peer tracking,
retry policy, evidence replay, catch-up scheduling, and sync triggering can be
designed for this repository's validator, network, and observability needs.
Those choices may trade simplicity, bandwidth, latency, and recovery speed, as
long as they only change how evidence is obtained and never change what
evidence means.

When comparing this implementation with Tendermint or CometBFT, always ask
which layer is being compared:

```text
if it is a safety rule, copy the proven semantics
if it is liveness machinery, use the original as reference material
```

## Safety Invariants

These invariants are the highest-priority contract. Implementation choices are
valid only if they preserve them.

1. A block is committed only with a valid `CommitCertificate`.
2. A local chain height is advanced only by applying a verified
   `CommittedBlock`.
3. A `CommitCertificate` is valid only if it contains quorum precommits for the
   same `(height, round, block_hash)`.
4. A `PolkaCertificate` is valid only if it contains quorum prevotes for the
   same `(height, round, block_hash)`.
5. Duplicate votes from the same validator do not increase voting power.
6. Votes are scoped by `(height, round, vote_type)`.
7. Locks survive round increments within the same height.
8. Locks are cleared only after committing the height or abandoning the height
   through verified height sync.
9. A node may prevote a proposal only if it is unlocked, locked on the same
   block, or receives valid evidence that safely supersedes the lock.
10. A node may jump rounds only within the same height and only because of
    signed quorum evidence.
11. A future proposal alone is not enough to jump rounds.
12. Height catch-up is not a round catch-up fast path. It requires committed
    blocks and commit certificates.

## Evidence Model

Evidence is the durable protocol information that can be validated, stored,
gossiped, and used to derive safe actions.

### ProposalEvidence

```text
ProposalEvidence {
  height: u128
  round: u32
  proposer: Address
  block: Block
  block_hash: Hash
  valid_round: Option<u32>
  valid_round_certificate: Option<PolkaCertificate>
  signature: Signature
}
```

`valid_round` is the Tendermint-style valid round for the proposed block. When
present, it must be backed by a `PolkaCertificate` for the same height and block
hash at a lower round than the proposal round.

The current prototype calls this proposal justification. The production design
should make it an explicit certificate.

### SignedVote

```text
SignedVote {
  height: u128
  round: u32
  vote_type: Prevote | Precommit
  validator: Address
  value: Block(Hash) | Nil
  signature: Signature
}
```

Votes are stored as signed evidence. Certificates are derived from stored votes.

### PolkaCertificate

```text
PolkaCertificate {
  height: u128
  round: u32
  block_hash: Hash
  prevotes: quorum SignedVote(Prevote, Block(block_hash))
}
```

A polka certificate proves that a quorum prevoted for a block at a height and
round. It can justify future proposals and can update the node's valid value.

### CommitCertificate

```text
CommitCertificate {
  height: u128
  round: u32
  block_hash: Hash
  precommits: quorum SignedVote(Precommit, Block(block_hash))
}
```

A commit certificate proves that a quorum precommitted a block. A node may
commit only when it has both the commit certificate and the matching block.

### CommittedBlock

```text
CommittedBlock {
  block: Block
  commit_certificate: CommitCertificate
}
```

This is the unit of height sync. Applying a committed block verifies the commit
certificate, validates and executes the block, checks state hash, appends to the
local chain, and advances the local height.

## Validation Layers

Validation must stay layered. Mixing these checks makes the implementation hard
to audit.

### Stateless Validation

Stateless validation depends only on the message, fixed validator set, chain
configuration, and deterministic proposer selection.

It checks:

- canonical decoding
- signature validity
- validator membership
- proposer matches `(height, round)`
- vote shape is well-formed
- proposal block hash matches the proposed block

It does not decide whether the node should transition.

### Contextual Validation

Contextual validation depends on local chain and consensus context.

It checks:

- proposed block is valid on top of local chain tip
- proposal height matches expected block height
- proposal previous block hash matches local tip
- proposal `valid_round` is lower than proposal round
- proposal `valid_round_certificate` matches the proposal block hash
- evidence height matches the consensus height being evaluated

### Quorum Validation

Quorum validation turns stored votes into certificates.

It checks:

- votes have the same height, round, type, and value
- validator duplicates are ignored or rejected
- validator count reaches quorum
- all signatures were already verified or are verified before certificate
  construction

### Transition Validation

Transition validation decides what local state may change.

It checks:

- whether a proposal may be prevoted
- whether a lock may be created
- whether a lock may be superseded
- whether a round jump is safe
- whether a commit is possible
- whether the node should enter height sync

## Runtime Boundaries

### MessageValidation

Owns stateless validation of inbound messages. It converts raw network messages
into validated evidence candidates.

It must not mutate consensus state.

### EvidenceStore

Owns stored evidence and certificate derivation.

Responsibilities:

- store proposals by `(height, round)`
- store prevotes and precommits by `(height, round, value)`
- deduplicate votes by validator
- derive `PolkaCertificate`
- derive `CommitCertificate`
- remember recent evidence for gossip
- expose evidence queries for catch-up

The store may contain evidence for current, future, and recently committed
heights. Retention policy is separate from safety rules.

### ConsensusCore

Owns safety-critical local state.

State:

```text
height
round
step
locked_round: Option<u32>
locked_block_hash: Option<Hash>
valid_round: Option<u32>
valid_block_hash: Option<Hash>
```

Responsibilities:

- apply local timeouts
- decide whether to prevote
- decide whether to precommit
- create or update locks
- update valid round/value from polka certificates
- commit with commit certificates
- decide whether a round jump is safe

It should not own networking, peer state, gossip loops, message broadcast,
message replay, or sync retry policy. Those are liveness concerns.

### ConsensusReactor

Owns network-facing consensus runtime behavior.

Responsibilities:

- receive messages
- call stateless validation
- insert evidence into `EvidenceStore`
- ask `ConsensusCore` what actions are now safe
- run gossip loops
- track peer status
- schedule local timeouts

The reactor may trigger core actions, but it does not invent safety rules. Its
job is to turn network activity into validated evidence and to keep peers
supplied with evidence they are likely missing.

### BlockSync

Owns height catch-up.

Responsibilities:

- fetch committed blocks from peers
- verify commit certificates
- execute blocks against local chain state
- append verified blocks
- restart consensus at `tip + 1`

Block sync is separate from round catch-up. Round catch-up stays within one
height. Block sync advances chain height.

## Derived Actions

New evidence should be reduced into a small set of actions.

```text
DerivedAction:
  EnterRound(height, round)
  ProcessProposal(height, round)
  Prevote(height, round, value)
  Precommit(height, round, value)
  Commit(CommittedBlock)
  RequestBlock(height, block_hash)
  StartHeightSync(target_height)
```

Adding future fast paths should mean adding better evidence-to-action derivation,
not adding special cases in unrelated code.

## Normal Consensus Path

1. Start height `h`, round `0`, step `Propose`.
2. The proposer builds and signs a proposal.
3. Receivers validate and store `ProposalEvidence`.
4. If the proposal is valid and lock rules permit it, they prevote the block.
5. `EvidenceStore` derives a `PolkaCertificate` once quorum prevotes the block.
6. `ConsensusCore` updates valid value and lock state as appropriate.
7. Nodes precommit the block if rules permit it.
8. `EvidenceStore` derives a `CommitCertificate` once quorum precommits the
   block.
9. If the matching block is known, `ConsensusCore` emits `Commit`.
10. Chain applies `CommittedBlock` and starts height `h + 1`.

## Lock And Unlock Rules

The exact lock rules are the core safety contract.

### Lock Creation

A node locks on block `B` at round `r` when it observes a valid
`PolkaCertificate(height, r, hash(B))` and is willing to precommit `B`.

### Prevote Rule

A node may prevote proposal `B` at `(height, round)` if one of the following is
true:

1. The node is not locked.
2. The node is locked on `hash(B)`.
3. The proposal carries a valid `PolkaCertificate` for `hash(B)` at a round
   greater than the node's `locked_round` and lower than the proposal round.

Otherwise the node prevotes nil.

### Unlock Rule

A node may supersede its lock only when it receives valid quorum evidence for
the same height at a higher round than the lock. A proposal alone does not
unlock. A peer status claim does not unlock.

### Valid Round Rule

When a node observes a valid `PolkaCertificate(height, r, block_hash)`, it may
record:

```text
valid_round = r
valid_block_hash = block_hash
```

The proposer for a later round should propose the valid block with
`valid_round = r` when it has the block.

## Round Catch-Up Path

Round catch-up is same-height recovery.

Future evidence is first stored, not discarded. After insertion, the reactor
asks the core/store whether any safe action is now available.

Allowed round catch-up triggers:

1. A valid future proposal with a valid `PolkaCertificate`.
2. A valid future `PolkaCertificate` for a known block.
3. A valid future `CommitCertificate`.

Round catch-up must not be triggered by:

- proposal alone
- peer status alone
- a single vote
- local wall-clock assumptions about another node

If a future commit certificate is available and the block is known, the node may
commit without waiting through each intermediate round. If the block is unknown,
the node requests the block and keeps the certificate.

## Commit Catch-Up Path

Commit catch-up handles the case where a peer at the same height already has
enough precommits to commit.

The required evidence is:

- matching block
- `CommitCertificate` for the block hash

If either side is missing:

- known certificate but missing block: request or gossip the block
- known block but missing certificate: keep block and wait for precommits

Once both are present, the node commits the block and advances height.

## Height Sync Boundary

Height sync begins when a node is behind an already committed chain height.

Examples:

- peer reports a committed height greater than local height
- node receives committed block evidence for height greater than local height
- node has missed enough heights that consensus gossip is no longer the right
  recovery mechanism

Height sync uses `CommittedBlock` sequences:

```text
local_tip + 1
local_tip + 2
...
target_height
```

Each committed block must be verified and applied in order. Height sync is the
only path that advances local chain height by applying already committed blocks.

Consensus gossip may help discover that sync is needed, but block application
belongs to the sync path.

## Gossip Strategy

The first production-ish gossip design can remain simple.

### Initial Gossip

When a node creates or receives valid evidence:

- store it
- broadcast it once immediately
- keep it in recent evidence cache

### Periodic Rebroadcast

Every small interval, rebroadcast recent evidence for:

- current height
- current round and recent rounds
- commit certificates for recently committed heights

This is intentionally wasteful but simple. Duplicate votes are already safe to
ignore.

### Peer-Aware Gossip

Later, add peer status:

```text
PeerStatus {
  height
  round
  step
  known_proposal_rounds
  known_prevote_rounds
  known_precommit_rounds
}
```

Then gossip can target missing evidence instead of rebroadcasting everything.

Peer status is not trusted for safety. It is only a hint for what to send.

## Simulation Scenarios

The simulator should classify failures by missing evidence, not by ad hoc
symptoms.

Scenarios:

1. No faults: all validators commit the same height sequence.
2. Delay only: validators eventually commit or catch up using stored evidence.
3. Duplicate only: duplicates do not alter voting power.
4. Reorder only: future evidence is stored and later applied.
5. Low drop rate: gossip rebroadcast eventually recovers missing votes.
6. One validator delayed: delayed validator catches up within the same height
   using round catch-up or commit catch-up.
7. One validator misses a height: block sync catches it up with committed
   blocks.
8. Missing block but known commit certificate: node requests block before
   commit.
9. Known block but missing commit certificate: node waits or requests votes.
10. Byzantine-style duplicate/conflicting votes: conflicting behavior is
    detected and does not increase voting power.

## Rejected Shortcuts

### Trust Peer Status For Progress

Rejected. Peer status is not signed quorum evidence. It can guide gossip but
cannot justify locks, commits, or jumps.

### Treat Future Proposal Alone As A Jump Trigger

Rejected. A future proposer can be valid but still lacks quorum evidence.

### Replay Raw Network Logs As Catch-Up

Rejected as the core model. Catch-up should be based on stored evidence and
certificates, not timestamped message replay.

### Mix Height Sync Into Round Catch-Up

Rejected. Height sync changes chain state and must verify committed blocks in
order. Round catch-up only changes consensus position within one height.

### Add Special Fast Paths Directly To State Machine

Rejected. Fast paths must be expressible as evidence-derived actions.

## Relationship To Current Prototype

The current prototype already contains:

- lock
- polka-like proposal justification
- quorum prevote to lock/polka
- quorum precommit to commit
- future input buffering

The next design step is to formalize and separate responsibilities:

- turn justification into explicit `PolkaCertificate`
- turn commit into explicit `CommitCertificate`
- introduce `EvidenceStore`
- move future evidence handling out of direct state-machine branching
- derive safe actions from stored evidence
- add commit certificate propagation
- define the height sync boundary

The current implementation can be used as a behavioral sketch, but the final
architecture should be evidence-store driven.

## Implementation Slices

### Slice 1: Certificate Types And Validation

- Add explicit `SignedVote`, `PolkaCertificate`, and `CommitCertificate` model.
- Define validation functions for each layer.
- Keep existing happy path behavior.

### Slice 2: EvidenceStore

- Store proposals and votes by height and round.
- Deduplicate votes.
- Derive polka and commit certificates.
- Add unit tests for quorum derivation and duplicate handling.

### Slice 3: Core/Store Boundary

- Make `ConsensusCore` consume current safe actions rather than raw future
  messages.
- Keep lock and unlock logic in the core.
- Keep evidence collection in the store.

### Slice 4: Round Catch-Up

- Store future evidence.
- Derive safe `EnterRound` or `Commit` actions from certificates.
- Add delay/reorder simulation tests.

### Slice 5: Commit Propagation

- Store committed blocks and commit certificates.
- Gossip commit certificates.
- Allow lagging validators to commit once they have block plus certificate.

### Slice 6: Height Sync

- Define committed block fetch.
- Apply committed blocks in order.
- Restart consensus at local tip plus one.

### Slice 7: Peer-Aware Gossip

- Add peer status.
- Target missing evidence.
- Reduce periodic rebroadcast noise.

## Open Issues

1. Exact Tendermint valid-round semantics should be checked against the original
   algorithm before finalizing the lock superseding rule.
2. Commit certificate wire format can be explicit or derived from individual
   precommit messages. The safety model is the same, but implementation and
   bandwidth differ.
3. Evidence retention policy is not defined yet.
4. Byzantine evidence handling for double-signing is not designed yet.
5. Validator set changes remain out of scope.

## Next Step

Before implementation, review and tighten:

1. lock and unlock rule wording
2. `PolkaCertificate` and proposal `valid_round` shape
3. `ConsensusCore` versus `EvidenceStore` ownership
4. exact action derivation order when multiple certificates appear at once

Once those are agreed, begin with Slice 1 and Slice 2. Do not add catch-up fast
paths until certificate derivation is explicit and tested.
